ROOT CAUSE ANALYSIS
Confirmed directly from the original source:
1. WorkManagerAutoBackupScheduler reduced ENQUEUED and RUNNING to one Boolean, isManualBackupActive. SettingsScreen rendered that Boolean as an indefinite Backing up... spinner. Therefore a queued job with an unmet network constraint appeared to be uploading. BLOCKED was omitted from the active-work predicate.
2. Wi-Fi Only mapped to NetworkType.UNMETERED, not a Wi-Fi transport check. Android can classify Wi-Fi as metered. Such a connection can prevent the worker from starting. Cellular connectivity was never required.
3. AutoBackupWorker returned success without uploading whenever automatic backup was disabled, even for manually requested work. New requests explicitly carry MANUAL, AUTOMATIC or TEST type; only AUTOMATIC honors the automatic-enable switch.
4. Result.retry() had no attempt limit. The transport used blocking execute(), had no total call timeout, and enabled automatic connection retries. These were reliability and duplicate-delivery risks. The prior source already used unique KEEP work for manual requests, so duplicate unique-work enqueue was not proven to be the cause of the reported duplicate emails.
5. The original UI had no worker stages, cancellation control, persistent history or distinction between queued work and a network upload.

Not proven: the actual WorkInfo state, metered classification, battery restriction, stale-work condition or server behavior on the user's phone. No device/logs were available. The source proves the misleading spinner mechanism, but does not establish which constraint or restriction affected that particular phone. Do not interpret this report as physical-device reproduction or verification.

ARCHITECTURE AUDIT AND FINAL FLOW
SettingsScreen -> BackupStatusCard -> SettingsViewModel.enqueueBackup -> AutoBackupScheduler.enqueueBackup -> unique one-time WorkManager work using KEEP -> AutoBackupWorker -> BackupFileManager -> existing ExportSessionUseCase / ExportValidator / CsvEventExporter -> BackupRepository -> HttpBackupProvider / OkHttp -> nonempty UTF-8 text/csv POST -> HTTPS redirects -> response classification -> persistent BackupRun metadata and worker output -> observed WorkInfo + DataStore history -> SettingsUiState.

Preparation uses the existing sanitization/export pipeline. No new backup encryption or compression was introduced. The SQLCipher database and Keystore token storage remain in place. The temporary CSV is plaintext in the app-private cache and is transmitted over HTTPS. It is deleted on worker completion/cancellation/error; abandoned files are handled by the existing stale-file cleanup. No second CSV copy is retained for history.

Test Connection: existing lightweight GET path, independent reachability status and response time; it neither invokes the CSV exporter nor marks a backup successful.
Send Test Backup: BackupFileManager creates only test,status,timestamp plus InputMonitor,OK and a timestamp. The worker then uses the same BackupRepository and HttpBackupProvider POST/authentication/redirect/response path as real backups. It cannot read real records through the synthetic-file branch. Test uploads are labeled TEST in history and do not advance the real-backup last-success timestamp.
Automatic: existing independent unique periodic work, approximately every 24 hours, UPDATE policy, unmetered-or-connected network constraint and battery-not-low constraint. A shared process mutex serializes simultaneous automatic/manual uploads. Automatic scheduling is not cancelled by the manual Cancel action.

NEW UI
Only the backup portion of Settings was replaced. It uses existing Material 3 cards, switches, typography and buttons.
- Destination shows Google Apps Script or Custom HTTPS Endpoint without exposing the URL. Configuration and GET reachability are separate from backup success. Destination details offer explicit Copy URL; credentials are hidden, and the token entry is masked.
- Status shows the current stage, progress semantics, session/record counts and actual generated byte size; duration, attempts and sanitized failure information remain visible after completion.
- Manual waiting work has a clear reason and Cancel. Try Again replaces the primary action after failure. An already-sent request may still finish at the server after local cancellation; the UI explains this.
- Last successful backup and last attempt remain separate.
- Send Test Backup and Test Connection are separate actions.
- Automatic status includes the WorkManager next eligible time when available, explicitly approximate. Relevant power/background restriction hints are shown for queued work.
- Wi-Fi Only explains Android's actual unmetered-network semantics and applies to manual, test and automatic requests. The switch is disabled while manual work is active, so a queued request does not silently retain an unexpected old constraint.
- History keeps up to 100 attempts, provides View All, and opens metadata-only Backup Details. It includes success, failure and cancellation metadata, byte sizes, HTTP status and retry counts. Details include start/completion times, duration, type, counts and work ID.
- Corrected the old zero-network-transmission and encrypted-CSV descriptions; neither accurately described the existing configured cloud-backup behavior.

STATE FLOW AND PROGRESS
Idle(0) -> Queued(5) -> Preparing(15) -> Exporting(30) -> Prepared(45) -> Uploading(60) -> WaitingForServer(90) -> Success(100).
Branches: WaitingForNetwork(5), WaitingForWifi(5), Retrying(5), Failed(0), Cancelled(0).
Progress is stage-based, not byte-based. No timer generates percentages. Uploading is emitted when the request body is written; WaitingForServer is emitted after the body is flushed to the transport. This does not mean Gmail has acknowledged delivery. Only a successful HTTP response without a recognized script-level error results in Success/100. Failures never display successful 100 percent. No numeric uploaded-bytes counter is claimed.

FILE SIZE
BackupFileManager obtains size from finalFile.length() after the UTF-8 exporter has flushed and closed its output. The worker records this Long as sizeBytes and uploadSizeBytes. These are identical because this pipeline does not compress or encrypt the CSV payload. The synthetic fixture uses toByteArray(Charsets.UTF_8) before writing. No String.length is used as the backup byte size. KB/MB labels use 1024-based units. The session count represents distinct sessions in the exported rows, not empty sessions that have no rows.

WORKMANAGER MAPPING
ENQUEUED -> WaitingForNetwork if the default network is not validated; WaitingForWifi if unmetered is required but the network is metered; Retrying after a prior attempt; otherwise Queued with Android scheduling guidance.
BLOCKED -> Queued with prerequisite-work explanation; remains active and prevents another manual enqueue.
RUNNING -> observed worker progress stage; Preparing before the first progress update.
SUCCEEDED -> Success from output metadata. A successful no-op without metadata stays Idle instead of claiming a completed upload.
FAILED -> Failed using output/history metadata and a sanitized explanation.
CANCELLED -> Cancelled. Queued jobs that never entered a worker are reconciled into history when the ViewModel observes their terminal state.

Worker progress is written through WorkManager progress Data and to DataStore. Terminal metadata is also in output Data. The ViewModel observes unique work and history on creation; navigation or recreation does not enqueue work. Tests cover reattachment to existing snapshots and repository recreation. Actual OS process-kill restoration remains a device-validation gate.

WI-FI / BATTERY BEHAVIOR
Wi-Fi Only OFF: CONNECTED; metered Wi-Fi qualifies and no cellular connection is needed.
Wi-Fi Only ON: UNMETERED; validated unmetered Wi-Fi qualifies, metered Wi-Fi waits. Other unmetered transports also qualify because this is the retained Android constraint, not strict Wi-Fi transport enforcement.
Disconnected/captive connection: the UI reports Waiting for internet connection. Reconnection updates the network snapshot and WorkManager controls resumption.
Automatic work also requires battery not low. Manual work does not add that constraint. Default-network callbacks and power/background-restriction broadcasts update diagnostic hints. Manufacturer-specific restrictions cannot be conclusively inferred, and no battery/security controls are bypassed or changed automatically.

DUPLICATE PREVENTION, RETRIES AND CANCELLATION
Manual and test uploads share the existing unique one-time work name with KEEP. All unfinished states prevent another active manual job. A synchronous atomic guard also rejects rapid clicks while enqueue is being submitted, and enqueue-operation failures are surfaced. Automatic work retains its separate periodic name.
CSV filenames now use UUIDs so simultaneous preparations cannot collide within one second. A process mutex serializes manual/automatic uploads.
OkHttp connection retry is disabled. The POST body is one-shot. A stable Idempotency-Key is sent for the same run. The existing Apps Script-style POST -> 302 -> GET response redirect remains covered by a passing network test. Replaying a POST through a body-preserving redirect is intentionally avoided.
Safe transport failures before sending the body may retry up to three total worker attempts with existing WorkManager backoff. The UI exposes the next attempt. HTTP error responses after a POST, and failures/timeouts after body transmission begins, are not automatically replayed because server side effects may already have occurred. They return a usable failure state. An interrupted prior upload is likewise not blindly resent on worker restart.
IMPORTANT: a client cannot guarantee exactly one email after all crashes, network interruptions or explicit retries unless the server honors idempotency keys. This work guarantees unique active manual client work and suppresses automatic ambiguous POST replay; it does not prove remote exactly-once delivery. Enabling automatic retries after ambiguous server-side failures requires server-side deduplication, which was outside the provided Android source and was not altered.
Cancel targets only the manual/test unique work name. Coroutine cancellation cancels the OkHttp Call, propagates through file generation, records sanitized metadata, and deletes the temporary file. Local cancellation cannot undo a request already accepted by Apps Script.

SECURITY AND OBSERVABILITY
HTTPS enforcement, normal certificate validation, optional bearer authentication, Keystore storage and database encryption are retained. HTTPS-to-HTTP redirects are disabled. Local HTTP is limited to exact loopback hosts for existing JVM fixtures; the production manifest still disallows cleartext traffic. No endpoint, token or secret was hardcoded.
Logs include UI request/enqueue, worker stage/attempt, export counts/bytes and HTTP response codes. Script error response bodies and transport exception messages are not copied into upload logs/history. No CSV contents or typed/accessibility content is added to progress/history.

REMAINING ISSUES / ACCEPTANCE LIMITS
- The exact phone-specific cause remains unverified; the misleading state mapping is fixed in source and unit-tested.
- No connected hardware or emulator was available, so the mandatory physical checks and instrumentation are not complete.
- Remote exactly-once Gmail delivery needs Apps Script/server idempotency support. The Android client cannot supply that guarantee alone.
- Progress is honest stage progress, not uploaded-byte progress. No fake byte counter is displayed.
- History is bounded to 100 attempts. It does not reconstruct older backups made before this metadata feature.
- Runtime behavior under OEM-specific restrictions, real OS process death, actual Apps Script/Gmail delivery and Compose accessibility needs device verification.
- The artifact is debug-signed and is not a production/store release.
